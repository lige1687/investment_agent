# 每日基金交易讨论室体验版设计

## 目标

为个人基金实盘建立一个“每天可发起、可参与、可追溯”的多 Agent 讨论室。系统围绕现有持仓回答两个核心问题：

1. 通信、纳斯达克等相关题材当前处于什么阶段。
2. 今天哪些持仓需要操作，以及买卖多少。

体验版默认采用影子运行和手动确认：系统可以生成立即操作、条件操作或今日不操作的计划，但不连接券商、不自动下单。只有机会明显、数据可信、账户允许且交易现实可行时才输出具体金额。

## 产品原则

- 默认结论允许且鼓励“今日不操作”。
- 多 Agent 用于专业分工、独立判断和发现分歧，不使用简单多数投票。
- DeepSeek 负责分析、讨论与解释；确定性政策引擎负责否决项、仓位上限、批次和金额校验。
- 用户参与目标仓位、阈值和交易纪律的讨论；任何政策修改都必须由用户确认并生成新版本。
- 第一阶段优先覆盖已有持仓和用户指定题材，不优先建设全市场基金推荐器。
- 第一阶段通过手工题材映射和指数绑定工作；完整基金持仓穿透后置。

## 体验版范围

### 包含

- 手动发起一次“今日讨论”。
- 冻结当次账户、市场、题材、净值、交易规则和个人政策快照。
- 专业 Agent 第一轮独立提交结构化意见。
- 展示共识、分歧、一票否决项和缺失数据。
- 用户在同一讨论室内追问、补充偏好或提出政策调整。
- 记录 Agent 生成结构化决策草案。
- 确定性政策引擎复算是否允许交易及最大金额。
- 主持 Agent 只总结通过校验的最终结果。
- 用户可将结果标记为接受、部分接受、忽略或仅观察。
- 保存证据、技能版本、政策版本、讨论记录和最终结果。

### 不包含

- 券商连接或自动下单。
- 全自动盘中高频监控。
- 依靠基金名称自动完成精细持仓穿透。
- Agent 自行修改目标仓位、风险线或评分阈值。
- 使用模拟或过期行情产生正式交易建议。
- 第一版自动从全市场推荐新基金。

## 每日讨论流程

```text
用户发起今日讨论
  -> Context Clerk 冻结同一时点的上下文快照
  -> Router 根据问题和持仓确定专业技能调用顺序
  -> 第一轮专业 Agent 独立提交结构化意见
  -> 系统提取共识、分歧、缺失数据和否决项
  -> 只围绕分歧点进行第二轮讨论
  -> 用户参与讨论并确认临时判断或政策修改建议
  -> Recorder 将讨论转换为结构化 DecisionDraft
  -> PolicyValidator 确定性复算动作、批次和金额
  -> Chair 总结已校验结论
  -> 用户接受、部分接受、忽略或观察
  -> 保存执行反馈，供后续复盘
```

第一轮 Agent 看见相同的只读上下文快照，但看不见其他 Agent 的结论，避免先发观点造成锚定和共识迎合。第二轮才允许围绕明确分歧互相质询。

## 专业 Agent 与已下载 Skills 映射

### 1. Router / Context Clerk

职责：识别用户意图、冻结数据、检查必填信息，并按优先级调度专业模块。

使用：

- `batch-trading-router`

必须遵守的优先级：账户风险 > 单标的风险 > 逻辑失效 > 市场环境 > 组合许可 > 止盈 > 批次规划 > 普通减仓 > 新买入热情。

### 2. Market Regime Agent

职责：判断整体市场环境和账户可承担的风险，不直接决定单只基金买卖。

使用：

- `batch-trading-market-regime`
- 现有市场、指数、宏观和行业轮动数据工具

输出市场评分、市场状态、总仓位上限、买入分数门槛、现金偏好和数据置信度。

### 3. Theme Research Agent

职责：使用题材专属模板判断通信、纳斯达克、全球资产等题材阶段。

使用：

- 现有 `hithink-industry-query`
- 现有 `hithink-sector-selector`
- 现有 `news-search`
- 现有 `report-search`
- 市场环境 Agent 的约束结果

输出题材阶段：筑底、启动、主升、过热、震荡、退潮或趋势破坏；同时输出支持证据、反证、数据时间和置信度。

### 4. Portfolio Risk Agent

职责：根据账户持仓、现金、目标仓位和题材暴露判断是否允许新增风险以及最大空间。

使用：

- `batch-trading-position-risk`

硬性检查包括总仓位上限、账户回撤线、现金底线、同题材暴露和单标的账户风险。

### 5. Buy and Batch Agent

职责：只在市场环境与组合风险通过后评估买入或加仓，并规划独立批次。

使用顺序：

- `batch-trading-buy-signal`
- `batch-trading-batch-planner`

用户当前偏好是“只在机会明显时操作”。因此体验版比技能默认规则更保守：只有买入评分达到 80 分以上、同时达到市场状态要求且无否决项时，才允许产生“立即操作”；65–79 分最多产生“条件操作”，低于 65 分只观察。用户确认后的个人政策可以继续提高门槛，但不能绕过技能的风险否决项。

### 6. Sell and Protection Agent

职责：判断止损、止盈、逻辑失效或账户降风险是否触发，并生成卖出执行顺序。

按触发来源使用：

- `batch-trading-stop-loss`
- `batch-trading-take-profit`
- `batch-trading-sell-execution`

卖出执行 Agent 不得自行创造卖出理由；只有上游风险、止损、止盈或逻辑失效模块给出触发后，才能决定卖哪一批、卖多少和资金返回哪里。

### 7. Skeptic Agent

职责：不增加新的综合分数，专门寻找：

- 数据错期、模拟或过期。
- 证据重复计数。
- 单日追涨和叙事过度。
- 同题材集中度被不同基金名称掩盖。
- 交易成本、限购、在途订单或冷却期被忽略。
- 建议与个人政策冲突。

Skeptic 只能增加反证、降低置信度或提出否决候选，不能直接生成操作金额。

### 8. Recorder / Chair

Recorder 将讨论转换为结构化草案；Chair 将 PolicyValidator 的结果转成用户可读总结。两者都不能覆盖确定性校验结果。

## Skill 加载与版本控制

- 新增只读的 `TradingSkillRegistry`。
- 根目录通过 `TRADING_SKILL_ROOT` 配置，默认解析为 `~/.codex/skills`。
- 只允许加载白名单中的八个批次交易技能及其直接引用的规则文件。
- 服务启动时读取完整 `SKILL.md` 与所需 reference，计算 SHA-256 内容哈希。
- 每个 SpecialistMemo 保存实际使用的 skill 名称和哈希。
- 缺少、读取失败或哈希变化未重新确认时，该角色返回 `unavailable`，不得静默改用通用提示词。
- Skills 作为角色的系统约束，不作为可被用户聊天覆盖的普通文本。

## DeepSeek 接入

现有 `OpenAICompatClient` 与 `LLMRegistry` 已支持 DeepSeek 基础协议，体验版在此基础上扩展讨论室角色。

### 模型选择

- 默认分析角色：`deepseek-v4-flash`。
- 默认主持与记录角色：体验版同样使用 `deepseek-v4-flash`，保持成本和延迟可控。
- 保留按角色配置 `deepseek-v4-pro` 的能力，但不作为体验版必需条件。
- 不使用即将在 2026-07-24 弃用的 `deepseek-chat` 和 `deepseek-reasoner` 旧模型名。

DeepSeek 官方当前支持 OpenAI 格式的 `/chat/completions`、JSON Output 和 Tool Calls。工具参数即使使用模型生成也必须在本地通过 Pydantic 校验；体验版不依赖 Beta strict 模式，避免将正式决策链建立在 Beta 接口上。

官方参考：

- https://api-docs.deepseek.com/api/create-chat-completion
- https://api-docs.deepseek.com/guides/tool_calls
- https://api-docs.deepseek.com/quick_start/pricing

### 配置与安全

- `LLM_PROVIDER=deepseek`
- `LLM_MODEL=deepseek-v4-flash`
- `LLM_API_KEY` 只从后端环境变量读取。
- API Key 不进入数据库、前端响应、错误消息或日志。
- 为讨论角色新增独立配置覆盖，但默认继承全局 DeepSeek 配置。
- 分析温度默认 0.1；主持总结默认 0.2。
- 输出结构解析失败时只允许一次格式修复重试；再次失败则该角色标记为不可用。

## 同一时点上下文快照

一次讨论只能引用一个不可变快照，至少包含：

- `as_of` 和各市场交易日。
- 数据模式、来源、新鲜度、是否模拟。
- 持仓、成本、当前仓位、现金、账户净值和账户回撤。
- 已知在途订单和最近操作时间。
- 题材及指数行情。
- 基金净值和交易规则。
- 当前个人交易政策版本。
- 实际使用的 skill 版本哈希。

A 股、海外指数和 QDII 净值必须分别标注市场时间，不能伪装成同一实时价格。缺少关键时间或关键数据时，快照状态为 `incomplete`，讨论可以继续解释，但 PolicyValidator 只能给出观察或不操作。

## 基金与题材映射的阶段性方案

体验版不建设完整持仓穿透，采用以下方式：

- 指数基金和 ETF 联接基金绑定明确跟踪指数。
- 主动主题基金由用户确认一个主题材和最多两个次题材。
- 保存 `mapping_source=user_confirmed`、确认时间和备注。
- 日常题材判断基于该映射，但界面明确提示主动基金可能发生风格漂移。
- 后续通过基金净值与题材指数的滚动相对表现发现疑似漂移，再接季度持仓穿透。

基金映射缺失时，不允许对该基金产生题材驱动的立即操作建议。

```json
{

  "status": "PASS",
  "verdict": "允许小幅增加风险",
  "score": 78,
  "confidence": 0.84,
  "positive_signals": ["总仓位低于震荡市上限"],
```

## 确定性 PolicyValidator

PolicyValidator 不调用 LLM。它按下载技能规定的优先级和用户确认政策执行：

1. 账户回撤和生存线。
2. 单标的账户风险。
3. 同题材暴露。
4. 市场状态和总仓位上限。
5. 买入/加仓或卖出触发前置条件。
6. 批次身份、止损、止盈和卖出计划。
7. 交易成本、限购、在途订单和冷却期。
8. 最小操作金额。

体验版内置的基础硬规则来自现有 skills：

- 账户回撤 5% 为警戒线，7%–8% 为降风险线，10% 为生存线。
- 单标的账户风险原则上不超过账户的 5%，计算方式为标的仓位 × 止损宽度。
- 买入前必须存在止损位置和卖出计划。
- 新买入至少保留目标仓位的 20% 作为灵活资金，不一次满仓。
- 不同买入时间、成本和理由必须保存为不同批次。
- 卖出优先级为账户风险 > 单标的止损 > 逻辑失效 > 利润保护 > 高低切换 > 普通减仓。
- 止损后至少等待 3–5 个交易日，并按新批次重新评分。

### 动作类型

- `OPERATE_NOW`：数据完整，无否决项，机会达到用户的明显门槛，金额校验通过。
- `CONDITIONAL`：方向成立但仍缺价格、确认日或其他触发条件；不得显示为已建议立即成交。
- `NO_ACTION`：条件不足、仓位无需调整或存在否决项，同时说明下一触发条件。

### 金额计算

```text
基础可操作仓位 = min(
  目标仓位 - 当前仓位,
  单次分批上限,
  市场总仓位剩余额度,
  题材风险剩余额度,
  单基金风险剩余额度,
  现金可用额度
)

最终操作仓位 = 基础可操作仓位
  × 买入分数允许部署比例
  × 题材阶段系数
```

结果必须再检查最小操作金额、费用和在途订单。金额计算的每个输入都在最终卡片中可展开查看。

## 个人交易政策与聊天确认

体验版初次运行时，缺失的政策值由 Agent 一次只询问一个问题。政策至少包含：

- 总仓位目标区间和现金底线。
- 每个题材的目标仓位与上限。
- 每只基金的目标仓位与上限。
- 单次分批上限和最小操作金额。
- 买入明显机会门槛。
- 操作冷却期。
- 止损宽度、批次和卖出偏好。

Agent 可以在讨论中提出 `PolicyChangeProposal`，包含旧值、新值、理由和影响。只有用户点击确认后才创建新版本；新政策不追溯修改过去的决策记录。

## 页面设计

新增“今日讨论室”页面，复用现有 Agent 聊天、证据抽屉和决策卡组件。

页面从上到下包含：

1. 数据快照状态：时间、来源、缺失和是否可用于正式判断。
2. 今日持仓候选：由风险和变化筛选需要讨论的持仓，不代表必须交易。
3. Agent 圆桌：逐个显示专业角色的结论、证据、反证和缺失数据。
4. 共识与分歧：只突出会改变动作的争议。
5. 用户讨论区：允许追问、调整临时假设或提出政策修改。
6. 最终决策区：显示立即操作、条件操作或今日不操作，以及金额计算过程。
7. 用户反馈：接受、部分接受、忽略、观察。

第一版只提供手动“开始今日讨论”按钮，不自动定时运行。

## 后端边界

新增独立模块，避免继续扩大当前 `agent_service.py`：

- `trading_room/context.py`：冻结上下文。
- `trading_room/skill_registry.py`：加载并校验技能。
- `trading_room/orchestrator.py`：控制独立首轮、分歧轮和用户轮次。
- `trading_room/specialists/`：各专业角色。
- `trading_room/policy.py`：确定性政策校验和金额计算。
- `trading_room/schemas.py`：快照、Memo、草案和结果契约。
- `trading_room/store.py`：会话、消息、版本和反馈持久化。

体验版 API：

- `POST /api/v1/agent/trading-room/sessions`：创建并运行第一轮。
- `GET /api/v1/agent/trading-room/sessions/{id}`：读取完整讨论状态。
- `POST /api/v1/agent/trading-room/sessions/{id}/messages`：用户参与讨论。
- `POST /api/v1/agent/trading-room/sessions/{id}/finalize`：生成草案并执行政策校验。
- `POST /api/v1/agent/trading-room/sessions/{id}/actions`：记录用户反馈。
- `GET/POST /api/v1/agent/trading-policy`：读取政策、提交并确认版本变更。

## 持久化

新增数据实体：

- `TradingRoomSession`：状态、快照、政策版本、模型、技能版本和最终结果。
- `SpecialistMemoRecord`：角色、结构化意见、证据和错误状态。
- `TradingRoomMessage`：用户与 Agent 的讨论记录。
- `TradingPolicyVersion`：不可变政策版本。
- `PolicyChangeProposalRecord`：待确认和已确认的政策变更。

现有 DecisionCard、EvidenceBus 和用户动作记录继续复用，最终通过校验的结果可以生成兼容的 DecisionCard。

## 失败与降级

- 数据源失败或返回模拟数据：允许讨论数据缺失，但结果只能是 `NO_ACTION`。
- 任一关键风险 Agent 不可用：不得生成立即买入或加仓。
- 非关键研究 Agent 失败：展示缺失角色并降低置信度，可生成观察结论。
- DeepSeek 返回非法结构：本地校验失败后只重试一次；再次失败则记录角色不可用。
- 多 Agent 严重分歧且无法通过事实解决：输出 `CONDITIONAL` 或 `NO_ACTION`，不通过平均分强行表决。
- PolicyValidator 与 Chair 文本冲突：前端只展示 PolicyValidator 的结构化动作，并记录主持总结错误。
- API 超时：会话保持可恢复状态，已完成角色结果不丢失。

## 测试策略

遵循 TDD，先写失败测试。

### 后端

1. SkillRegistry 只加载白名单技能并记录内容哈希。
2. 缺失技能时相关角色 fail closed。
3. 第一轮 Specialist 看不到其他 SpecialistMemo。
4. 所有角色引用同一个不可变快照。
5. DeepSeek 工具参数和 JSON 输出必须通过 Pydantic 校验。
6. 结构错误只重试一次，API Key 不出现在日志或响应。
7. 市场环境、组合风险、买入和批次严格按技能顺序调用。
8. 账户风险和止损否决优先于任何高买入分数。
9. 80 分以下不会产生体验版立即买入。
10. 金额计算不突破目标仓位、现金、总仓位和单标的风险上限。
11. 数据不完整或模拟时只能观察或不操作。
12. 同样快照和政策输入得到相同 PolicyValidator 结果。
13. 政策修改必须用户确认并生成新版本。

### 前端

1. 正确展示各 Agent 的独立状态、分歧、证据和缺失信息。
2. `NO_ACTION` 不使用买入或卖出的强行动配色。
3. 条件操作明确展示触发条件和失效条件。
4. 金额计算可展开且字段缺失不导致页面崩溃。
5. 未确认的政策提案不会显示为当前政策。
6. DeepSeek/API 错误不泄露密钥或原始请求。

### 验证

- 后端单元测试和相关集成测试。
- 前端 Vitest 与 TypeScript 构建。
- 浏览器完成一次包含共识、分歧、用户追问和最终 `NO_ACTION` 的完整流程。
- 浏览器完成一次达到 80 分但被仓位风险否决的流程。
- 先以影子模式完成至少 10 次有效日度讨论，并覆盖至少一次“风险否决高分买入”的场景，再决定是否将建议用于真实操作。

## 体验版成功标准

1. 用户可以一键开始当天讨论，并看见各角色正在做什么。
2. 每个结论都能追溯到数据证据、skill 版本和个人政策版本。
3. 同一轮所有 Agent 使用同一时间快照。
4. Agent 之间存在分歧时不通过简单投票掩盖。
5. 最终金额由确定性引擎计算，不由总结 Agent 自由生成。
6. 数据不可信、关键角色失败或风险否决时不会产生正式买入建议。
7. 用户可以通过聊天讨论阈值，但只有明确确认后才改变政策。
8. DeepSeek API 可配置、可替换，服务端不泄露密钥。
9. 第一版能够覆盖易方达信息产业、纳斯达克相关基金及其他手工绑定题材的现有持仓。

## 实施顺序

1. 先完成已有 P0 数据可信层，确保模拟数据和正式行情彻底隔离。
2. 建立 TradingSkillRegistry、结构化 schemas 和确定性 PolicyValidator。
3. 接入 DeepSeek 新模型名和讨论室角色配置。
4. 建立上下文快照、独立首轮和分歧汇总。
5. 实现讨论室 API、持久化和个人政策版本。
6. 实现前端讨论室体验。
7. 以影子模式进行浏览器复测和实际使用观察。

## 风险与控制

- 多 Agent 增加成本和延迟：只对当天需要讨论的持仓调用相关角色；无分歧不运行第二轮。
- 多 Agent 产生伪共识：第一轮隔离，证据按来源去重，不使用简单投票。
- 主动基金题材漂移：体验版显示手工映射来源和确认时间，后续补相对表现与持仓穿透。
- Skill 内容变化导致行为变化：保存哈希并在会话中显示版本。
- DeepSeek 模型更新导致输出漂移：模型名、参数和响应摘要随会话保存；确定性规则保持独立。
- 用户在聊天中临时改变纪律：临时偏好不能覆盖硬规则；政策变更必须显式确认和版本化。
