# 每日基金交易讨论室体验版设计

## 目标

为个人基金实盘建立一个“每天可发起、可参与、可追溯”的多 Agent 讨论室。系统围绕现有持仓回答两个核心问题：

1. 通信、纳斯达克等相关题材当前处于什么阶段。
2. 今天哪些持仓需要操作，以及买卖多少。

体验版默认采用影子运行和手动确认：系统可以生成立即操作、条件操作或今日不操作的计划，但不连接券商、不自动下单。只有机会明显、数据可信、账户允许且交易现实可行时才输出建议区间。

## 产品原则

- 默认结论允许且鼓励“今日不操作”。
- 多 Agent 用于专业分工、独立判断和发现分歧，不使用简单多数投票。
- DeepSeek 负责分析、讨论、建议操作区间与解释；交易前预检和轻量交易护栏检查申赎状态、目标仓位上限和实际可用资金，最终金额由用户确认。
- 用户参与目标仓位、阈值和交易纪律的讨论；任何政策修改都必须由用户确认并生成新版本。
- 第一阶段优先覆盖已有持仓和用户指定题材，不优先建设全市场基金推荐器。
- 指数基金按跟踪指数映射；主动基金按“最新公开持仓 + 净值风格推断”动态判断主题暴露，手工映射只作为无法获取数据时的低置信度后备。

## 体验版范围

### 包含

- 手动发起一次“今日讨论”。
- 冻结当次账户、市场、题材、净值、最新公开持仓、申赎状态和个人政策快照。
- 专业 Agent 第一轮独立提交结构化意见。
- 展示共识、分歧、一票否决项和缺失数据。
- 用户在同一讨论室内追问、补充偏好或提出政策调整。
- 记录 Agent 生成结构化决策草案。
- 最终输出前重新执行申赎状态预检，轻量交易护栏检查建议区间是否超过当日限额、目标仓位上限或实际可用资金。
- 主持 Agent 展示护栏校验后的建议区间，用户决定最终金额。
- 用户可将结果标记为接受、部分接受、忽略或仅观察。
- 保存证据、技能版本、政策版本、讨论记录和最终结果。

### 不包含

- 券商连接或自动下单。
- 全自动盘中高频监控。
- 声称能够获得主动基金当天的真实调仓明细。
- Agent 自行修改目标仓位、风险线或评分阈值。
- 使用模拟或过期行情产生正式交易建议。
- 第一版自动从全市场推荐新基金。

## 每日讨论流程

```text
用户发起今日讨论
  -> Context Clerk 冻结同一时点的上下文快照
  -> Exposure Engine 计算最新公开与推断的主题暴露
  -> Execution Preflight 获取当前申购、赎回、限购和暂停状态
  -> Router 根据问题和持仓确定专业技能调用顺序
  -> 第一轮专业 Agent 独立提交结构化意见
  -> 系统提取共识、分歧、缺失数据和否决项
  -> 只围绕分歧点进行第二轮讨论
  -> 用户参与讨论并确认临时判断或政策修改建议
  -> Recorder 将讨论转换为结构化 DecisionDraft
  -> Execution Preflight 再次刷新交易状态
  -> LightTradeGuard 检查当日限额、目标仓位上限和实际可用资金
  -> Chair 总结已校验结论
  -> 用户选择最终金额，并接受、部分接受、忽略或观察
  -> 保存执行反馈，供后续复盘
```

第一轮 Agent 看见相同的只读上下文快照，但看不见其他 Agent 的结论，避免先发观点造成锚定和共识迎合。第二轮才允许围绕明确分歧互相质询。

## 专业 Agent 与已下载 Skills 映射

### 1. Router / Context Clerk

职责：识别用户意图、冻结数据、检查必填信息，并按优先级调度专业模块。

使用：

- `batch-trading-router`

Router 保留技能中的风险优先思想，但体验版不启用强制批次流程，也不把技能中的默认风险额度自动写成用户政策。未由用户确认的阈值只作为专业意见展示。

### 2. Market Regime Agent

职责：判断整体市场环境和账户可承担的风险，不直接决定单只基金买卖。

使用：

- `batch-trading-market-regime`
- 现有市场、指数、宏观和行业轮动数据工具

输出市场评分、市场状态、总仓位上限、买入分数门槛、现金偏好和数据置信度。

### 3. Theme Research Agent

职责：使用题材专属模板判断通信、纳斯达克、全球资产等题材阶段。

使用：

- 现有 `hithink-industry-query`
- 现有 `hithink-sector-selector`
- 现有 `hithink-fund-query`
- 现有“基金分析与筛选”中的风格漂移检测框架
- 现有 `news-search`
- 现有 `report-search`
- 市场环境 Agent 的约束结果

输出题材阶段：筑底、启动、主升、过热、震荡、退潮或趋势破坏；同时输出支持证据、反证、数据时间、公开持仓截止日、推断主题暴露和置信度。

### 4. Execution Availability Agent

职责：在讨论开始和最终输出前检查基金是否真的可以买卖，以及当日最多可申购多少。

使用：

- `announcement-search`
- `hithink-fund-query`

输出固定结构：申购状态、赎回状态、单日限额、适用客户类型、适用份额类别、生效日期、恢复状态、公告标题、公告 URL、发布时间和查询时间。该角色不评价机会好坏。

必须按生效日期对“暂停、调整、恢复”公告排序并还原当前状态，不能因为搜到一条历史限购公告就认定今天仍然限购。无法确定当前状态时返回 `UNKNOWN`，不得产生可执行买入金额。

### 5. Portfolio Risk Agent

职责：根据账户持仓、现金、目标仓位和题材暴露提供风险意见，指出集中度、回撤和现金压力。

使用：

- `batch-trading-position-risk`

技能中的总仓位、账户回撤、同题材暴露和单标的风险规则作为讨论依据。风险指标先由确定性代码计算，再由 Agent 解释并给出观察、减仓或退出建议。只有用户通过默认模板或聊天明确确认的阈值才成为当前策略，未确认的技能默认值只显示为参考。

### 6. Buy Agent

职责：结合市场环境与组合风险意见评估买入或加仓，并提出建议操作区间、触发条件和失效条件。

使用：

- `batch-trading-buy-signal`

用户当前偏好是“只在机会明显时操作”。体验版以 80 分作为“明显机会”的初始讨论门槛：达到 80 分且关键专业意见不存在未解决的反对项时，才可以提出“立即操作”；65–79 分最多提出“条件操作”，低于 65 分只观察。这个分数不是金额公式，用户可以在讨论中确认或调整门槛。

`batch-trading-batch-planner` 不进入体验版决策流程。每次操作只记录日期、金额、理由、题材阶段和用户决定，暂不强制标记核心批、确认批或高位批。

### 7. Sell and Protection Agent

职责：从止损、止盈、逻辑失效和账户风险角度提供卖出意见，并提出减仓区间、触发条件与失效条件。

使用：

- `batch-trading-stop-loss`
- `batch-trading-take-profit`

体验版不调用要求明确批次身份的 `batch-trading-sell-execution`。Sell and Protection Agent 只根据当前总持仓提出减仓区间、理由和触发条件，具体金额由用户确认。

### 8. Skeptic Agent

职责：不增加新的综合分数，只审查证据真实性和推理链漏洞：

- 数据错期、模拟或过期。
- 证据重复计数。
- 原始数据不能支持 Agent 声称的结论。
- 推理中存在自相矛盾、遗漏关键前提或因果倒置。
- 限购、在途订单、公告生效日期或持仓报告期被误读。
- 不同 Agent 引用了同一个来源，却被当作多项独立证据。

Skeptic 不得因为“大盘位置高”“宏观环境一般”等独立观点调整微观题材 Buy 分数；这些观点只能由 Market Regime Agent 提出。Skeptic 不得生成新市场观点、修改其他 Agent 分数、提出仓位建议或直接生成操作金额。每条质疑必须引用具体 `evidence_ref` 或明确指出缺失字段，否则不进入正式分歧列表。

### 9. Recorder / Chair

Recorder 将讨论转换为结构化草案；Chair 将 LightTradeGuard 校验后的建议区间转成用户可读总结。两者都不能把超过申购限额、目标仓位或可用资金的金额展示为可执行金额。

## Skill 加载与版本控制

- 新增只读的 `TradingSkillRegistry`。
- 批次交易技能根目录通过 `TRADING_SKILL_ROOT` 配置，默认解析为 `~/.codex/skills`；行情与公告技能根目录通过 `MARKET_SKILL_ROOT` 配置，默认解析为 `~/.openclaw/workspace/skills`。
- 只允许加载体验版白名单中的 Router、市场环境、仓位风险、买入、止盈、止损、`hithink-fund-query`、`announcement-search` 和“基金分析与筛选”技能及其直接引用文件。批次规划和卖出执行技能保留在本地，但体验版不调用。
- 服务启动时读取完整 `SKILL.md` 与所需 reference，计算 SHA-256 内容哈希。
- 每个 SpecialistMemo 保存实际使用的 skill 名称和哈希。
- 缺少、读取失败或哈希变化未重新确认时，该角色返回 `unavailable`，不得静默改用通用提示词。
- Skills 作为角色的系统约束，不作为可被用户聊天覆盖的普通文本。

## DeepSeek 接入

现有 `OpenAICompatClient` 与 `LLMRegistry` 已支持 DeepSeek 基础协议，体验版在此基础上扩展讨论室角色。

### 模型选择

- 默认分析角色：`deepseek-v4-flash`。
- 默认主持与记录角色：体验版同样使用 `deepseek-v4-flash`，保持成本和延迟可控。
- 保留按角色配置 `deepseek-v4-pro` 的能力，但不作为体验版必需条件。
- 不使用即将在 2026-07-24 弃用的 `deepseek-chat` 和 `deepseek-reasoner` 旧模型名。

DeepSeek 官方当前支持 OpenAI 格式的 `/chat/completions`、JSON Output 和 Tool Calls。工具参数即使使用模型生成也必须在本地通过 Pydantic 校验；体验版不依赖 Beta strict 模式，避免将正式决策链建立在 Beta 接口上。

官方参考：

- https://api-docs.deepseek.com/api/create-chat-completion
- https://api-docs.deepseek.com/guides/tool_calls
- https://api-docs.deepseek.com/quick_start/pricing

### 配置与安全

- `LLM_PROVIDER=deepseek`
- `LLM_MODEL=deepseek-v4-flash`
- `LLM_API_KEY` 只从后端环境变量读取。
- API Key 不进入数据库、前端响应、错误消息或日志。
- 为讨论角色新增独立配置覆盖，但默认继承全局 DeepSeek 配置。
- 分析温度默认 0.1；主持总结默认 0.2。
- 输出结构解析失败时只允许一次格式修复重试；再次失败则该角色标记为不可用。

## 同一时点上下文快照

一次讨论只能引用一个不可变快照，至少包含：

- `as_of` 和各市场交易日。
- 数据模式、来源、新鲜度、是否模拟。
- 持仓、成本、当前仓位、现金、账户净值和账户回撤。
- 已知在途订单和最近操作时间。
- 题材及指数行情。
- 基金净值、公开持仓报告期、推断主题暴露和交易规则。
- 基金管理人申赎状态、限额公告及销售渠道确认状态。
- 当前个人交易政策版本。
- 实际使用的 skill 版本哈希。

A 股、海外指数和 QDII 净值必须分别标注市场时间，不能伪装成同一实时价格。缺少关键时间或关键数据时，快照状态为 `incomplete`，讨论可以继续解释，但系统只能给出观察或不操作。

## 动态主题暴露引擎

主动基金公开信息无法提供当天真实调仓。监管部门也明确提示，第三方净值估算通常基于上一季度公开持仓，而基金经理会动态调整组合，因此不能把披露持仓伪装成实时持仓。体验版采用双轨主题暴露：

### 公开披露暴露

- 使用 `hithink-fund-query` 获取最新报告期、前十大重仓股、持仓占比和行业分类。
- 使用基金公司或监管披露的最新季度、半年度或年度报告校验报告期。
- 返回结果必须同时包含 `report_period_end` 和 `published_at`；缺失报告期的数据不能进入正式主题权重。
- 将重仓股按统一行业与题材分类聚合，得到 `reported_exposure`。
- 指数基金和 ETF 联接基金直接使用跟踪指数及其最新成分权重，标记为 `index_tracked`。

### 净值风格推断

- 使用基金净值与候选题材指数进行 60 个交易日滚动回归和相关性分析。
- 输出各题材 beta、解释度 R²、窗口截止日和稳定性变化。
- 推断结果只表示基金近期收益行为更接近哪些题材，不等同于真实持仓。
- 当公开披露与净值推断明显冲突时，标记 `style_drift_suspected`，降低题材结论置信度。

### 暴露置信度

- `HIGH`：指数跟踪关系明确；或主动基金报告期距当前不超过 60 天、R² 不低于 0.80，且披露与推断方向一致。
- `MEDIUM`：报告期距当前不超过 120 天且 R² 不低于 0.70，或两条证据只部分一致。
- `LOW`：报告期超过 120 天、报告期缺失、R² 低于 0.70或出现明显风格漂移。
- 手工主题标签只作为先验信息和搜索提示，不能覆盖公开披露与净值推断。

主题暴露为 `LOW` 时，题材 Agent 可以讨论可能影响，但不得把该题材作为立即操作的核心依据。

本机实测 `hithink-fund-query` 可以返回001513的重仓股、申万行业和行业占比，但同一查询没有返回可靠的持仓截止日期。因此实现必须将“报告期缺失即不可作为正式主题权重”写成数据校验，不能把最新净值日期误当成持仓日期。数据来源：同花顺问财。

监管参考：

- https://www.csrc.gov.cn/shenzhen/c105614/c7602038/content.shtml
- https://www.csrc.gov.cn/csrc/c101954/c7619929/content.shtml

## 交易前申赎状态预检

讨论开始时先取得一次状态，最终生成建议前必须绕过普通缓存再次刷新。预检结果结构为：

```json
{
  "fund_code": "001513",
  "share_class": "A",
  "manager_status": "LIMITED",
  "daily_purchase_limit_yuan": 10000,
  "customer_scope": "ALL",
  "effective_at": "2026-06-25",
  "channel_status": "UNKNOWN",
  "source_title": "调整大额申购及大额转换转入业务限制的公告",
  "source_url": "https://...",
  "published_at": "2026-06-25T00:00:00+08:00",
  "fetched_at": "2026-07-13T14:30:00+08:00"
}
```

规则：

- `announcement-search` 查询基金代码、全称、暂停申购、限制大额申购、调整限额和恢复申购公告。
- 只接受基金代码和份额类别精确匹配的公告；按生效日期排列状态变化，计算当前基金管理人状态。
- `hithink-fund-query` 用作第二来源或补充交易字段，不得用搜索结果排序分数代替公告生效顺序。
- 讨论最终化时的基金管理人状态查询不得早于 15 分钟；超过 15 分钟必须重查。
- `SUSPENDED`：买入结果强制为 `NO_ACTION`。
- `LIMITED`：护栏后金额不得超过当日剩余限额。
- `UNKNOWN`：只能生成 `CONDITIONAL`，要求用户在实际销售渠道确认。
- 基金管理人公告不能保证支付宝、天天基金等销售渠道没有更低的平台限制。没有销售渠道 API 时，页面必须把 `channel_status` 标记为 `UNKNOWN`，不能声称“保证可下单”；用户确认平台状态后才能把计划标记为可执行。

本机已验证 `announcement-search` 能检索出易方达信息产业混合A(001513)的大额申购限制变化；2026-07-13 的验证样本中，2026-06-25 生效的公告将单日单账户A/C类申购上限调整为1万元。该结果只作为解析测试夹具，运行时必须重新查询。数据来源为同花顺问财，最终卡片必须保留公告原始链接和查询时间。

## 轻量交易护栏 LightTradeGuard

LightTradeGuard 不调用 LLM，也不判断机会好坏。它只防止建议金额明显越过已经确认的交易边界。

体验版只有三类硬约束：

1. 基金管理人状态不能为暂停申购；有限额时不能超过当日剩余额度。销售渠道状态必须已自动验证或由用户明确确认。
2. 买入或加仓后不能超过用户确认的基金或题材目标仓位上限。
3. 买入金额不能超过扣除在途订单后真实可用的现金；卖出金额不能超过当前实际持仓。

系统不内置单次操作上限，不内置单标的风险额度，不根据止损宽度自动计算仓位，也不强制批次分类。专业 skills 中的相关规则由各 Agent 作为风险意见展示，只有用户在聊天中明确确认某条规则后，它才会进入个人政策。

### 动作类型

- `OPERATE_NOW`：数据完整，机会达到用户确认的明显门槛，专业分歧已解决，申赎状态已确认且建议区间通过轻量护栏。
- `CONDITIONAL`：方向成立但仍缺价格、确认日或其他触发条件；不得显示为已建议立即成交。
- `NO_ACTION`：条件不足、仓位无需调整、数据不可信或专业分歧未解决，同时说明下一触发条件。

### 建议区间与护栏裁剪

```text
Agent 建议区间 = 专业讨论形成的方向性区间

买入硬上限 = min(
  用户确认的目标仓位上限 - 当前仓位,
  扣除在途订单后的真实可用现金占比,
  当日申购剩余额度占账户比例
)

护栏后建议区间 = Agent 建议区间与 [0, 买入硬上限] 的交集
```

如果交集为空，结论为不操作；如果区间被截断，界面同时展示 Agent 原建议和截断原因。系统不从区间中自动选择最终金额，用户在讨论结束时确认实际金额。

## 个人交易政策与聊天确认

体验版不通过每日追问逐项冷启动。首次进入时提供一个可一次导入的 `mid-term-theme-v1` 默认模板，用户在单页确认或修改后生成 `personal-policy-v1`。政策至少包含：

- 总仓位目标区间和现金底线。
- 每个题材的目标仓位与上限。
- 每只基金的目标仓位与上限。
- 买入明显机会门槛。
- 用户希望长期保留的现金金额或比例。

Agent 可以在讨论中提出 `PolicyChangeProposal`，包含旧值、新值、理由和影响。只有用户点击确认后才创建新版本；新政策不追溯修改过去的决策记录。

题材和单基金目标仓位无法从通用模板可靠推断，在首次涉及该题材时只询问一次并保存，不在后续日常讨论中重复询问。

## 默认策略模板与风险建议

`mid-term-theme-v1` 来自用户已下载的批次交易 skills，但删除用户已明确否定的单次操作上限和强制批次分类。默认内容为：

- 明显买入机会初始门槛：80 分。
- 账户回撤 5%：警戒，风险 Agent 提醒检查高波动和同题材集中度。
- 账户回撤 7.5%：降风险，讨论室优先讨论减仓，不优先寻找新买入。
- 账户回撤 10%：保护状态，停止生成立即买入，先输出账户风险处理建议。
- 止损优先级：投资逻辑失效 > 题材中期趋势有效破坏 > 用户确认的百分比止损。
- 趋势有效破坏初始定义：关键趋势位下方连续收盘 2–3 个交易日、跌破幅度超过 2%–3%且不能快速收回，或放量跌破；具体关键位由题材和基金类型确定。
- 百分比止损默认关闭，只有用户明确设置某只基金或某类题材的阈值后才启用。
- 不设置单次操作上限，不自动计算复杂风险预算，不强制核心批、确认批或高位批。

### 风险 Agent 每日输出

- 账户从历史高点的当前回撤，以及命中的模板等级。
- 单只基金占账户比例、持有收益、从持有期高点的回撤和相关题材总暴露。
- 投资逻辑是否仍成立、题材趋势是否有效破坏。
- 三种结论之一：`NORMAL`、`RISK_REVIEW`、`REDUCE_OR_EXIT_CANDIDATE`。
- 触发依据、建议减仓区间和解除风险状态所需条件。

### 单标的风险

体验版不为了得到一个精确数字而虚构止损宽度。风险 Agent 同时展示仓位集中度、历史波动、持有期回撤和题材相关性；如果用户已经确认某个止损或逻辑失效位置，再额外计算 `标的仓位 × 预期损失宽度`。未设置止损宽度时明确显示“无法计算账户损失额度”，但仍给出集中度和回撤建议。

风险阈值产生建议和讨论优先级，不自动下单。用户导入模板即视为确认上述账户回撤控制；后续修改必须通过 `PolicyChangeProposal` 版本化。

## 页面设计

新增“今日讨论室”页面，复用现有 Agent 聊天、证据抽屉和决策卡组件。

页面从上到下包含：

1. 策略状态：首次进入可一键导入 `mid-term-theme-v1`，集中展示和修改全部初始阈值。
2. 数据快照状态：时间、来源、缺失和是否可用于正式判断。
3. 动态主题暴露：最新公开报告期、行业权重、净值推断、风格漂移和置信度。
4. 申赎状态：基金管理人状态、当日限额、销售渠道状态、公告来源和查询时间。
5. 今日持仓候选：由风险和变化筛选需要讨论的持仓，不代表必须交易。
6. Agent 圆桌：逐个显示专业角色的结论、证据、反证和缺失数据。
7. 共识与分歧：只突出会改变动作的争议；Skeptic 质疑单独标注证据问题，不混入市场观点。
8. 用户讨论区：允许追问、调整临时假设或提出政策修改。
9. 最终决策区：显示立即操作、条件操作或今日不操作，以及 Agent 建议区间、申赎状态、护栏后区间和用户最终金额。
10. 用户反馈：接受、部分接受、忽略、观察。

第一版只提供手动“开始今日讨论”按钮，不自动定时运行。

## 后端边界

新增独立模块，避免继续扩大当前 `agent_service.py`：

- `trading_room/context.py`：冻结上下文。
- `trading_room/exposure.py`：公开持仓聚合、净值风格推断和暴露置信度。
- `trading_room/execution_preflight.py`：公告状态机、限额和销售渠道确认。
- `trading_room/risk_metrics.py`：账户回撤、基金回撤、集中度和已确认风险公式。
- `trading_room/skill_registry.py`：加载并校验技能。
- `trading_room/orchestrator.py`：控制独立首轮、分歧轮和用户轮次。
- `trading_room/specialists/`：各专业角色。
- `trading_room/guard.py`：申赎状态、目标仓位和可用资金的轻量护栏。
- `trading_room/schemas.py`：快照、Memo、草案和结果契约。
- `trading_room/store.py`：会话、消息、版本和反馈持久化。

体验版 API：

- `POST /api/v1/agent/trading-room/sessions`：创建并运行第一轮。
- `GET /api/v1/agent/trading-room/sessions/{id}`：读取完整讨论状态。
- `POST /api/v1/agent/trading-room/sessions/{id}/messages`：用户参与讨论。
- `POST /api/v1/agent/trading-room/sessions/{id}/finalize`：生成草案并执行轻量护栏校验。
- `POST /api/v1/agent/trading-room/sessions/{id}/actions`：记录用户反馈。
- `GET /api/v1/agent/trading-policy/templates`：读取可导入策略模板。
- `POST /api/v1/agent/trading-policy/import`：一次导入并确认默认模板。
- `GET/POST /api/v1/agent/trading-policy`：读取政策、提交并确认版本变更。

## 持久化

新增数据实体：

- `TradingRoomSession`：状态、快照、政策版本、模型、技能版本和最终结果。
- `SpecialistMemoRecord`：角色、结构化意见、证据和错误状态。
- `TradingRoomMessage`：用户与 Agent 的讨论记录。
- `TradingPolicyVersion`：不可变政策版本。
- `PolicyChangeProposalRecord`：待确认和已确认的政策变更。
- `FundExposureSnapshot`：公开报告期、持仓聚合、净值推断和置信度。
- `FundTradeStatusSnapshot`：公告状态机、限额、渠道确认和来源。

现有 DecisionCard、EvidenceBus 和用户动作记录继续复用，最终通过校验的结果可以生成兼容的 DecisionCard。

## 失败与降级

- 数据源失败或返回模拟数据：允许讨论数据缺失，但结果只能是 `NO_ACTION`。
- 主动基金暴露置信度为 `LOW`：不得把题材判断作为立即操作的核心依据。
- 基金管理人状态为 `SUSPENDED`：买入只能为 `NO_ACTION`；状态为 `UNKNOWN` 或销售渠道未确认：买入最多为 `CONDITIONAL`。
- 公告搜索出现代码、份额类别或生效日期歧义：状态按 `UNKNOWN` 处理，不猜测当前限额。
- 任一关键分析 Agent 不可用：不得生成立即买入或加仓。
- 非关键研究 Agent 失败：展示缺失角色并降低置信度，可生成观察结论。
- DeepSeek 返回非法结构：本地校验失败后只重试一次；再次失败则记录角色不可用。
- 多 Agent 严重分歧且无法通过事实解决：输出 `CONDITIONAL` 或 `NO_ACTION`，不通过平均分强行表决。
- LightTradeGuard 与 Chair 文本冲突：前端只展示护栏校验后的结构化区间，并记录主持总结错误。
- API 超时：会话保持可恢复状态，已完成角色结果不丢失。

## 体验版成功标准

1. 用户可以一键开始当天讨论，并看见各角色正在做什么。
2. 每个结论都能追溯到数据证据、skill 版本和个人政策版本。
3. 同一轮所有 Agent 使用同一时间快照。
4. Agent 之间存在分歧时不通过简单投票掩盖。
5. Agent 给出建议区间，轻量护栏按申赎状态、当日限额、目标仓位和可用资金裁剪，最终金额由用户确认。
6. 数据不可信、关键角色失败或重大分歧未解决时不会产生正式买入建议。
7. 用户可以通过聊天讨论阈值，但只有明确确认后才改变政策。
8. DeepSeek API 可配置、可替换，服务端不泄露密钥。
9. 第一版能够根据最新公开持仓与净值风格推断覆盖易方达信息产业、纳斯达克相关基金和其他现有持仓，并明确暴露置信度。
10. 默认策略模板一次导入账户回撤和止损建议规则，不在每日讨论中重复查户口。
11. Skeptic 只审查证据真实性与逻辑漏洞，不用泛化宏观观点压低微观题材分数。

7. 实现前端讨论室体验。

## 风险与控制

- 多 Agent 增加成本和延迟：只对当天需要讨论的持仓调用相关角色；无分歧不运行第二轮。
- 多 Agent 产生伪共识：第一轮隔离，证据按来源去重，不使用简单投票。
- 主动基金不存在公开的当天调仓：明确区分最新披露与净值推断，报告期或推断质量不足时降低置信度。
- 基金管理人公告与销售渠道规则可能不同：自动校验基金管理人状态，渠道无接口时必须由用户确认，不能标记为保证可下单。
- Skill 内容变化导致行为变化：保存哈希并在会话中显示版本。
- DeepSeek 模型更新导致输出漂移：模型名、参数和响应摘要随会话保存；目标仓位和可用资金护栏保持独立。
- 用户在聊天中临时改变目标仓位：政策变更必须显式确认和版本化，未确认的临时说法不改变当前上限。
